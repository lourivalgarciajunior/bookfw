## Agent rules (mandatory)

These rules apply to every agent or AI assistant working in this project:

1. **Never start coding without a REQ and a ROADMAP.** If none exists, create them first.
2. **Use `/trackfw:implement <req-slug>` to start any implementation.** This skill orchestrates the full flow automatically: finds or generates the roadmap, moves it to `wip/`, executes each ML, updates the roadmap, and moves to `done/`.
3. **Only one roadmap in `wip/` at a time.** Before starting a new one, complete or move to `blocked/` the current one.
4. **Ciclo de vida do ML — obrigatório:**
   - Ao **iniciar** um ML: edite o roadmap alterando `**Status:** ⬜ Pendente` → `**Status:** 🔄 Em andamento` e faça commit do roadmap.
   - Ao **concluir** um ML: edite o roadmap alterando `**Status:** 🔄 Em andamento` → `**Status:** ✅ Concluído` e inclua essa mudança no commit do ML.
   - Ao **analisar** um roadmap antes de iniciar: mova o arquivo de `backlog/` para `analyzing/`; só mova para `wip/` ao começar a codificar de fato.
5. **Run `trackfw validate` before every commit.** Zero violations required.
6. **ADRs before decisions.** Any architectural or technical decision must have an ADR (`/trackfw:adr`).
7. **Obrigatório: Inspecione e respeite todos os ADRs globais nos diretórios listados em adr_dirs (inclusive caminhos ~/...) antes de propor alterações de arquitetura.**

## Branch strategy

One active branch at a time. Name it `feat/<slug>`, `fix/<slug>` or `refactor/<slug>`. Before creating a new branch, verify no other is genuinely open: run `git fetch origin --prune`, then `git branch -r --no-merged origin/main`, then for each candidate `git diff origin/main <branch> --stat`. An empty diff means it was squash-merged — ignore it. Squash merges do not mark a branch as merged, so `--no-merged` alone is not evidence. If the branch is stale and the diff looks inflated by main's own evolution, compare only the files the branch itself touched since the merge base.

## Definition of done

Green build and tests do not close a microbatch. It is done when the requirement and the roadmap sit in the correct state folder, their declared status matches that folder, the final validation is recorded with evidence, no duplicate copy remains in another state, and `trackfw validate` reports no violations.

## Requirement scope

Every requirement must declare an explicit negative scope: what must not be implemented. Boundaries prevent an implementing agent from inventing work.

## State requirements

`blocked` requires a reason and an owner. `abandoned` requires a reason and a successor. `wip` must reflect work that is genuinely active; anything stalled moves to `blocked` or `abandoned` instead of rotting in `wip`.

## Roadmap format

Organize work as waves of microbatches. A wave groups microbatches that can run in parallel; a barrier separates waves. Microbatches sharing any file — including generated trees and build outputs — must be sequential, and the reason is documented. Each microbatch declares exact files, exact actions, measurable acceptance criteria and exact validation commands, so that a small model can execute it without guessing.

## When governance is not required

A closed list of exemptions: a typo or local variable rename; a documentation-only change; a configuration tweak with no runtime effect; a direct revert; answering a question or reviewing without changes. Additionally, when the user reports a concrete bug, fix it directly and do not open an architectural analysis for it. **This section takes precedence over the general rule that requires a requirement and a roadmap.** Anything touching business logic, an API contract, a data schema, authentication or authorization, localization, or user-facing behavior always requires governance, regardless of how few files it touches.

## Production incidents

Inspect the live environment before proposing a fix: real variables, active credentials, granted permissions, running processes. Confirm the root cause against real evidence, then implement the smallest fix. Never edit static configuration files as a response to a root cause that has not been confirmed in the running environment.

## Iterative prototyping

For complex or uncertain user-facing work, validate the concept with a disposable, isolated prototype that the user reviews visually, and only then write the decision record and the production roadmap. Build and test success is not evidence that an interface is right.

## Autopilot

Ask everything you need before starting. Once started, do not interrupt for confirmations that could have been anticipated. Decide low-risk details autonomously following existing project conventions, and record autonomous decisions in the commit message.

## Architect responses

Default: what changed · what was decided · what is needed from you. Three to five lines.

Scale up only on these three triggers, and only on them: a **blocker** that stops the next wave; a **pending user decision** that cannot be inferred from context; an **error the architect made** that cannot be self-corrected.

Never cut, even when short: measured evidence (command and result), barrier verdict, decision taken and why. A response that buries a blocker in paragraph seven produced the same effect as not reporting it.

Cut: restating what an executor already reported, re-explaining reasoning already given, recapping state that has not changed, closing praise. Tables and code blocks only when they replace prose, never when they add to it.

Depth is on demand from the user.

## trackfw — Governance Rules

This project uses **trackfw** for AI-native delivery governance.
Chain: `ADR → REQ → ROADMAP` · States: `backlog / analyzing / wip / blocked / done / abandoned`

### Agent Protocol
1. **Before any implementation (mandatory):** create governance artifacts FIRST, then branch:
   `trackfw req new "title"` → `trackfw roadmap new "title"` → `trackfw roadmap move <name> wip` → `git checkout -b feat/<branch>`
   ❌ Never create a branch before REQ + ROADMAP are in wip/
   ❌ Never defer REQ/ROADMAP creation to a future task — they are prerequisites, not deliverables
   ✓ `trackfw validate` enforces this via `branch_has_wip_roadmap` rule (v2.7.0+)
2. **Before starting:** run `trackfw context` · read `docs/agents-working-context.md`
3. **After finishing:** update `docs/agents-working-context.md` with what changed
4. **Before PR:** `trackfw validate` must pass
5. **ML lifecycle — mandatory:**
   - Starting a ML: edit roadmap `**Status:** ⬜ Pendente` → `**Status:** 🔄 Em andamento` + commit.
   - Completing a ML: edit roadmap → `**Status:** ✅ Concluído` + include in ML commit.
   - Analyzing a roadmap: move from `backlog/` to `analyzing/`; to `wip/` only when coding starts.
6. **Obrigatório: Inspecione e respeite todos os ADRs globais nos diretórios listados em adr_dirs (inclusive caminhos ~/...) antes de propor alterações de arquitetura.**

### Architecture Directives (mandatory)
- **3-layer separation:** frontend / backend / database — never mix concerns
- **No in-memory data:** always database + ORM (never arrays/globals for persistence)
- **Auth from day 1:** never defer — refactoring auth later is very costly
- **Docker + .env from day 1:** containerize early; all config via env vars
- **2-layer validation:** frontend (UX) + backend (security) — never only one
- **API-first:** define OpenAPI contract before coding frontend/backend integration
- **Threat model waves:** every feature roadmap opens with a Wave 0 threat model (before implementation) and closes with a red-team review wave (before release)
- **Test coverage:** TDD for critical logic; min 60% (prototype) / 80% (production)
- Use `/trackfw:architect` to define stack before the first REQ

### Key Commands
- `trackfw context` — current governance state (always run first)
- `trackfw status` — all artifacts and states
- `trackfw validate` — governance consistency check
- `trackfw roadmap move <name> <state>` — transition roadmap state
- `trackfw serve` — live Kanban board at http://localhost:4080
